# Project architecture

This describes the current checkout, including local capability repairs. Requirements are in [prd.md](prd.md); verification status is in [tasks.md](tasks.md).

## Platform and modules

The application is primarily Kotlin with Jetpack Compose and native C/ASM integration. Existing scripts use AGP 8.13.2, Kotlin 2.0.21, Java 17 and compile SDK 36. ARM64 and minimum SDK 28 are configured. Direct builds target SDK 28; the playBuild switch targets SDK 36. Preserve these versions unless a task requires changing them.

### Codex account ownership

`CodexAccounts` stores metadata only in the private runtime root, using atomic replacement, opaque IDs, canonical containment and explicit symlink rejection. The validated legacy login remains at `/root/.codex`; new homes are `/root/.codex-accounts/<id>`. CLI login/status/logout, app-server catalogs/limits and execution receive their own CODEX_HOME and credential masking. These homes prevent accidental mixing, not access by hostile code under the same Android UID. New homes retain their own CLI configuration; harness prompt/skill snapshots and execution MCP overrides use the existing launch paths.

`providerJson` records `CHATGPT:<account-id>` at task admission; historical `CHATGPT` means the legacy home. Queued follow-ups capture the account in memory and retain the existing process-death behavior (unsent queue entries are not replayed). Runtime launches resolve the durable task binding and fail on missing/disabled/reconnect-required accounts. Native conversation scope uses account ID plus a persisted reconnect generation, never auth-file timestamps. No cross-account automatic retry exists.

The ChatGPT account card's persisted “Balance accounts” opt-in rotates task selection across usable enabled accounts using a durable fairness cursor. Selection skips only known exhausted spend controls or recent model/general quota windows; sparse reports merge, reset times are honored, and missing/stale quota data does not claim availability or exhaustion. Accounts are chosen when queued work is dispatched, then pinned in the task record; a retry/recovery never silently reselects another account. Native rate-limit events update per-account hints without adding polling. This opt-in does not apply to Custom API.

`CodexConversationHandoff` manages native context for saved ChatGPT chats, whether or not account balancing is enabled. Once ownership checks confirm the source process has closed, a complete bounded 0.161.0 rollout is validated for thread, workspace, version, records and snapshot hash. Transcript data alone is imported into the destination account's canonical sessions path and the same native thread ID resumes; source credential metadata is not required to validate the snapshot. Credentials, account configuration and account databases are never copied. If the native snapshot is missing, interrupted, ambiguous, changed or oversized, recovery waits for the task/process ownership gate, then may seed a fresh native thread in the same visible chat from bounded saved chat history. This restores saved text only and cannot recover hidden provider state. A failed final handoff must leave the chat able to accept later work. Native goal controls or child-thread state that cannot be resumed use ordinary fresh context with a notice; they are not reconstructed from the parent transcript. Latest-task checks prevent reuse of stale native context after another engine handled the chat; Claude and Antigravity use the same engine/route continuation rule. Project files remain in place, project Brain/rules stay shared, and account-specific credentials/configuration remain isolated. No universal lossless-continuity claim is made.

Authentication promotes a new account after CLI exit 0 and local `codex login status` confirms ChatGPT in that attempt's canonical home. File length, shared masks and legacy fallback cannot complete a new login; `account/read` only supplies optional display metadata. Legacy migration uses the same local status check. Unavailable status can preserve a previously verified selected login; explicit sign-out/wrong-auth status clears it and marks the ready record as needing sign-in. Status refresh keeps user labels.

Reconnect keeps the old metadata usable while signing into a fresh ID/home and replaces it only after success. Adding another account preserves a verified healthy default; a successful new login replaces an unusable old default, including records misclassified by earlier builds. Old private homes remain to avoid racing an orphan after process death. Interrupted unpublished logins are not selectable. Task ownership and model/usage results stay pinned to account IDs. Remove reaps its logout child, then removes that account's canonical credentials, known obsolete cache copies and metadata; CLI transcripts and project/chats remain.

`CredentialMounts.bindings` masks collection siblings individually using a fresh per-launch mask; it does not copy credentials or mask/rebind the active parent. Original guest homes and CLI resume paths are preserved. Existing account directory names remain visible, and PRoot is not an OS security boundary. Native process exit performs mask cleanup without following links. Failed Google attempts/account removal use the same no-follow deletion; account ID/home/token containment is validated before filesystem access. `AuthForegroundService` tracks separate login owners before stopping the existing service and also respects coding-task ownership. Antigravity serializes auth operations and validates saved credentials; GitHub replacement joins and reaps the prior attempt. Native/device acceptance remains separate from unit verification.

## Execution and ownership

Compose screens publish user intent through [MainViewModel](../app/src/main/java/com/jarves/mh/ui/MainViewModel.kt). [TaskSupervisor](../app/src/main/java/com/jarves/mh/runtime/task/TaskSupervisor.kt) coordinates task state, verification, recovery and the foreground task lifecycle. Engine bridges keep provider-specific launch/protocol behavior separate; native launch and PRoot run commands in the selected workspace.

A taskId identifies a supervised task; a sessionId identifies a process/provider session. They are distinct. Async publication also needs the applicable project, chat, root, engine, attempt and request ownership checks. Provider results, process outcomes and meaningful verification have distinct roles; a child or stream end_turn cannot terminate the parent by itself. Preserve completed Codex turns when later cleanup produces a nonzero exit unless a proven protocol failure requires a change.

Task/step persistence, [StepVerifier](../app/src/main/java/com/jarves/mh/runtime/task/StepVerifier.kt), [RecoveryEngine](../app/src/main/java/com/jarves/mh/runtime/task/RecoveryEngine.kt), process supervision and bounded output work within TaskSupervisor. Startup reconciliation marks interrupted work and checks owned processes; stored state is not a guarantee of automatic continuation after process death. Foreground execution notifications and [WakeLockManager](../app/src/main/java/com/jarves/mh/runtime/task/WakeLockManager.kt) belong to the task lifetime.

The inspector consumes RuntimeEvent updates, not an independent scheduler. MainViewModel's individual child/task termination methods currently report unsupported operation; full-task Stop uses the supervisor/bridge cleanup path. Usage combines reported token metrics with provider-specific reports/estimates; missing data must remain explicit.

The Codex app-server runner keeps native turn completion separate from process termination and goal completion. Native goals may continue across turns. Rules/Brain and attachments are injected before new goal activation; resume/status/pause/clear remain native control operations. RPCs, output and child close/reap have explicit bounds. Unsupported server requests fail visibly. Durable task schema version 3 adds nullable native command intent, preserving prior rows. Native operations use a single supervised step/attempt with no provider fallback/replay. Goal control references and Plan mode persist in the existing scoped preferences; ordinary resume references are consumed before an uncertain turn and restored only on success. Native Stop uses a task-scoped bounded graceful callback before generic termination. Turn-idle periods release the task wake lock while preserving connection ownership.

## Storage and context

- [AppPreferences](../app/src/main/java/com/jarves/mh/data/AppPreferences.kt) stores preferences/project metadata and a project chat index. Messages use pages; legacy whole-chat files remain readable and migrate through existing code.
- Chat messages may carry an optional WorkStatus outcome; missing or unknown values decode neutrally without changing legacy history. WorkPresentation supplies the testable presentation transform used by MainViewModel's existing supervisor finalization, after RuntimeSessionRouting.canFinish. Live status comes from owned supervisor/bridge updates and is not a new runtime state machine. Only active, visible work updates its elapsed timer; process termination remains owned by the runtime.
- [BrainContextAssembler](../app/src/main/java/com/jarves/mh/data/BrainContextAssembler.kt) creates bounded context from canonical tasks, progress, constraints and saved knowledge. Memory is contextual data, not higher-priority instructions.
- [WorkspaceCheckpoints](../app/src/main/java/com/jarves/mh/runtime/WorkspaceCheckpoints.kt) retains original-path inventory, backup provenance, fingerprints and canonical roots. Preserve schema compatibility and migrations.
- Credentials use the existing vault/Android Keystore integration and engine-specific homes. PRoot mount visibility does not isolate credentials against hostile native tools.
- [ContextMemoryStore](../app/src/main/java/com/jarves/mh/data/ContextMemoryStore.kt) and the memory sheet manage project user/automatic facts. [MemoryExtractor](../app/src/main/java/com/jarves/mh/data/MemoryExtractor.kt), retrieval/ranking/conflict handling and [BrainLearningService](../app/src/main/java/com/jarves/mh/data/BrainLearningService.kt) support the existing memory pipeline; canonical task/knowledge records are distinct from UI facts.
- Rule discovery includes AGENTS.md, CLAUDE.md and GEMINI.md, project .agents/.gemini/.claude rule directories and existing global/bundled locations. Project skill roots include .agents/skills, .claude/skills, .antigravity/skills, .gemini/skills and skills/; discovery also covers global, linked and bundled SKILL.md trees. Merge/project/global/custom scope and enabled selections are persisted; imported skills are copies, links reference other projects, and promotion copies into the global library.
- Codex reads local native skill metadata through a bounded 15-second app-server request before execution. The preparatory child is owned by the durable task/session, reaped through existing cleanup, and removed from health PID metrics without completing the task. Validated metadata feeds launch-local `skills.config` overrides; account config is not rewritten. Known disabled/unavailable/manual-only or shadowed paths and unmanaged repository skills are suppressed; restrictive scopes suppress unmanaged native skills, while merge mode preserves unmanaged non-repository native enablement. Native prior disablement is retained. Manual skills can still be invoked through the harness's explicit body/path envelope. Malformed/incomplete native inventory blocks execution rather than falling back to unrestricted discovery.
- SkillFiles shares bounded no-follow resource validation between imports and snapshots (256 entries, 8 MiB); SKILL.md/policy reads are capped at 128 KiB. Safe YAML parsing rejects custom object tags, duplicate keys, collection aliases and excessive nesting, handles multiline descriptions and reads invocation policy. Linked sources require registered-project ownership and canonical origin containment; linked selections recognize current IDs and earlier IDs. Guest global publication is restricted to declared skill directories, including legacy `.gemini/skills` access, without adding that legacy directory to catalog discovery or changing its precedence. Codex compact/goal/plan/review commands now use typed native app-server operations; the other engines retain their prompt workflows. See [the repairs](tasks.md#codex-command-and-skill-repairs--2026-10-13).
- Attachment files are copied into the project with bounded size/count and chat ownership; Android FileProvider grants read access when opening them. ZIP import/export have their own containment/exclusion checks and are not whole-app data backups.

## Native packaging

Normal Gradle assembly packages five prebuilt libraries from app/src/main/jniLibs/arm64-v8a/; externalNativeBuild is commented out. CMake describes their source build, but ordinary assembly does not establish source/binary equivalence. Retain binaries, vendored sources and licenses until a replacement is verified.

## Verification and distribution

Online/offline flavors share app behavior and differ in runtime delivery. Default debug uses com.jarves.mh.dev; stable release uses com.jarves.mh. Offline inputs are verified against their pinned manifest. Required phone/build commands are in [rules.md](rules.md).

Antigravity's pinned installation archive is packaged only in the offline flavor. Online APKs use RuntimeInstaller's existing verified download path when Antigravity is selected for installation; already-installed runtimes are reused. Offline asset preparation includes Antigravity in the same manifest verification and copying task as the other runtime archives.

Optional stacks in Models.kt are Web, Python, Android, C/C++ and PHP. Web uses the included Node.js/npm stack. Runtime assets/toolchains are distinct from the app's own Gradle dependencies. Bundled runtime delivery does not make provider requests offline.

Device frame timing uses the separate benchmark app after setup:

    gradle :app:installOnlineBenchmark
    gradle :benchmark:connectedBenchmarkAndroidTest -Pandroid.injected.androidTest.leaveApksInstalledAfterRun=true

Results and Perfetto traces appear under benchmark/build/outputs/connected_android_test_additional_output/. The existing target is P90 frame overrun at or below zero. These commands require working device access.

For local updater testing, preserve the signer, increase the installed version code, serve an HTTPS manifest, use the debug Settings override, and restore the normal update channel afterward. scripts/serve-update-server.sh uses host-specific shell utilities; confirm those on the target host before running it.
